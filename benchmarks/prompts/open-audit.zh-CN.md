# 开放审计提示词（发现不足与改进机会）

请独立审计附件中的 deterministic-pixel-art Skill。目标是找出有证据的不足和有价值的改进，也记录成立的设计取舍；不预设它一定有问题。请实际生成/编辑图像并保留产物，不能只根据功能清单写评价。

先说明你的平台、平台可见模型名称、是否真的能看图、是否能执行命令、OS、Python/Pillow、包 SHA-256。精确版本/token 不可获得时写未知。读附件自己的 SKILL.md 与按需资料。若无运行环境，只做标明“未实测”的静态审计；若无视觉能力，不宣称审美通过。

本次审计范围由协调者选择：

- 可靠性与可移植性：尺寸/坐标/边界、错误输入、依赖、Unicode 路径、覆盖保护、多产物失败、并发使用。
- 文本分析与无损编辑：透明与半透明、隐藏 RGB、4/8 邻域、区域/单元坐标、输出预算、PNG 往返和布局一致性。
- 创作与像素 UI：剪影辨识、光影和材质、像素块与斜线、图标视觉重量、状态语义、场景背景、留白/内容区、Minecraft 浮雕与衔接。
- Skill 使用成本：入口是否容易选择、必要读取量、错误恢复、无效命令、实际修改轮次、输出是否便于继续编辑。

协调者未指定时，先选择最适合本环境的两个范围，说明选择。不要为了“全面”大量重复同类检查。建议首轮上限 45 分钟、30 次被测工具命令，至多两轮修正；能力/额度不足就缩小并明确记录。每个受测环境使用相同预算，不要求用满。不进行破坏工作区、全局安装或无界资源压力测试。

请完成以下工作：

1. 先做一个自选正常任务，再做一个 PNG 局部修改任务，确认基本工作流。选两项彼此不同的像素资产：通用图标/32×32 非对称精灵/多状态 UI/Minecraft 界面。需求、尺寸、背景、状态或材质在绘制前固定。不要直接把包内示例原样渲染当成自己的创作验证。
2. 对所选范围设计少量边界与负例。输入、期望、命令、输出、exit code 和错误记录逐项保存。只有实际命令产生的耗时/次数才能报告；token 无真实计量就不估算。原生环境失败与修改依赖/兼容垫片后的结果分开，补丁不静默覆盖原包。
3. 如果能够看图，检查原尺寸、整数放大、深浅及目标背景。记录图像方向、轮廓、材质、状态、关键内容或衔接的具体问题，给出位置和理由。最多生成两个局部改善候选，保持原图并记录改善的代价。若字体/游戏环境不可用，不声称完成文本适配或游戏内验收。
4. 核对文档与实际行为。区分明确契约违反、文档不清、已声明限制、风格偏好和未支持的新功能。动画、九宫格、自动铺砖、字体或审美评分只有在被承诺或当前任务需要时才构成缺口；不能仅因缺少就算 bug。
5. 优先提交 3–8 条最有价值的发现；不足 3 条按实际提交。允许全部通过或只有持平。不要平均成一个总分，不把“检查了多少项”当成覆盖率，不把单模型评价当普遍审美证据。

交付 `audit-report.md`、`findings.json`、环境记录、测试输入、规格、PNG、预览/差异、辅助脚本、命令及 stdout/stderr，并保留原始可见会话。可参照随附 findings-template.json；缺少的事实用 null，不能虚填。

报告每条发现应包含：

- 唯一编号与简短标题。
- 类别：像素错误/数据损失/可靠性/环境兼容/文档/工作流/视觉意见/新功能建议。
- 证据：已复现、静态依据、视觉意见、未验证。
- 复现输入和最短命令，期望与实际，exit code。
- 产物路径与相关像素/区域 `[x,y,w,h]`；源码位置只是辅助，不能代替复现。
- 影响范围、发生条件与严重度理由：数据损失/错误结果/任务阻断/额外步骤/视觉偏好。
- 一个可行的最小改进，以及如何验证有效、可能引入什么退步。

最后列出：已经有效的能力；前三项优先改进及依据；未测试/未证明之处。不要只给“增加更多功能、提高美感、优化性能”等无法验收的建议，也不要仅因规范更严格便认定降级。只有单版本时，不得声称升级后更好或更快。

开放审计是缺陷发现与创作反馈，不能代替固定 A/B 任务的发布验收。没有执行权限的审计意见仍有参考价值，但必须保持相应证据标签。
