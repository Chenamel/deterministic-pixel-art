你是本次像素资产工具的独立使用者。请实际执行附件中的局部修改任务，提交可复核的产物；不要只阅读源码后写总结。你无需证明该工具更好，失败、持平和额外成本均可如实提交。

## 本次配置

- 环境标识：{{ENVIRONMENT}}
- 平台实际提供的模型标识：{{MODEL}}
- 能力模式：{{MODE}}
- 任务 ID：{{TASK}}
- 包标签：{{PACKAGE}}

若实际模型/看图能力与配置不符，先纠正并说明，不沿用错误信息。无法获得精确模型版本时写平台可见名称及“精确版本未知”。无法执行代码/读写文件时，说明本次只能做静态意见，不声称完成实测。纯文本模式不得调用模型视觉/图像识别，也不得借助另一个视觉模型；允许用 Pillow 读取和计算像素。多模态模式仅在你实际能查看图片时使用。

## 环境与公平性

1. 将附件解压到任务临时目录；校验 `checksums.json` 中的文件 SHA-256。展开 `package.zip`，定位其 `deterministic-pixel-art/SKILL.md` 和 `scripts/pixel_art.py`。不要全局安装或覆盖用户已有 Skill。
2. 使用任务可用的 Python 和 Pillow。先确定本次会一直调用的 Python 可执行路径；虚拟环境中的记录器和被测命令均使用同一解释器。记录 OS、Python、Pillow 及模型可见版本。允许安装原包声明的依赖；不要静默修改运行时。若必须补丁，保留原生失败和补丁说明，另开标为 shim 的运行，不冒充原生通过。
3. 不读取其他包、验收答案、旧报告、其他 Agent 的解法；不联网寻找本任务的答案。包标签只是名义遮蔽，版本元数据仍可见；不要据此推断哪版应当获胜。
4. 阅读该版本自己的 Skill 入口，按需读取参考资料；不要假设它具备另一个版本的命令。普通 Python/Pillow 辅助脚本允许使用，必须记录其内容和调用，额外步骤也是成本。

## 实际执行

将以下路径替换成真实路径。`PYTHON` 是选定解释器，`RUNNER` 为 runner.py 的绝对路径，`RUN` 为本次全新输出目录，`PACKAGE_ZIP` 为 package.zip 的绝对路径。

```text
PYTHON RUNNER start --out RUN --task {{TASK}} --package {{PACKAGE}} --package-zip PACKAGE_ZIP --environment {{ENVIRONMENT}} --mode {{MODE}} --model "{{MODEL}}"
```

尽早 start，依赖准备耗时另记。读取 `task/request.md`，使用 `input.png`、`context.json`、`layout.json` 及任务确实提供的 `reference.png`。分析时可以通过记录器调用包内已有功能或自己的辅助脚本：

```text
PYTHON RUNNER run --out RUN -- PYTHON ABSOLUTE_SCRIPT_PATH ARGUMENTS...
```

所有被测命令和辅助分析命令均走 runner；不要用 `shell=True`、管道或别名代替真实可执行程序。子进程工作目录为 RUN，输入/脚本路径使用绝对路径。文件编辑、图像查看和无法通过 runner 的动作保留在可见会话中。

首次分析后、修改任何图片或规格之前，将初次定位保存为 `RUN/localization.json`：

```json
{"regions":[[0,0,1,1]],"reason":"填写实际定位依据；这里的坐标只是格式示例"}
```

坐标为整张输入图的 `[x,y,w,h]`。记录你认为最小的目标修改区域；如果任务要求替换整个命名单元，填该单元的区域。`regions` 支持多个区域，不把整图作为含糊的定位。允许明确表示未定位成功，不靠编造坐标掩盖不确定性。初次定位一经保存不再更改，后续发现放到 notes 中。至少一次实际修改/渲染命令应在该记录存在后通过 runner 执行。

只修改 request 要求的像素，保持原尺寸、其余像素、方向、状态顺序与内容区域。最多两个候选、两轮针对性修正，不要求用满预算。第一份可运行方案不算修正；发现问题后更改方案或像素算一轮，自动重复运行相同命令不算修正。第二个方案计入候选数；所有中间规格、图片和失败输出均保留。

输出至少包含：

- `final.json`：该版本可渲染的 JSON 规格。
- `final.png`：由 final.json 渲染的最终图片，不能只交手工改过而规格无法复现的 PNG。
- `localization.json`：初次定位，不能事后替换。
- `notes.md`：实际步骤、候选数、修正轮次、环境问题、看图能力与未完成项。
- `feedback.md`：下面格式的具体反馈。
- runner 生成的 `run.json`、`commands.jsonl` 和全部 stdout/stderr。
- 辅助脚本及所有中间产物；原始可见会话另附。

旧 layout 的内容摘要绑定输入图；修改后的图像不要继续冒用输入摘要。如果包支持输出新布局，可生成新记录；否则保留输入布局及你的明确说明。

成功后：

```text
PYTHON RUNNER finish --out RUN --candidates N --revisions R
```

只有平台提供真实 token 用量时才加 `--tokens COUNT`，否则省略。失败且已产生至少一个候选时，添加 `--failure-stage environment|localization|repair` 并保存部分文件。现有 runner 不能编码 0 个候选；若在产生候选前就失败，保留未 finish 的 run 和错误，notes 明确写“候选 0，运行未完成”，不要填 1 制造完整记录。若整个环境根本无法执行 runner，直接交能力限制与可见错误，不伪造 run.json。

## 反馈格式

每个不足分别列：现象、触发条件、期望行为、实际行为、最小复现命令/输入、证据文件/像素坐标、影响、建议和验证办法。注明证据类别：

- 已执行并复现。
- 静态源码/文档依据，尚未执行。
- 体验或审美意见，有具体图片/区域。
- 功能建议，当前未承诺支持。
- 因环境限制未验证。

没有问题时可以写“本次未发现”；不得为凑数发明缺陷。成功修好任务、覆盖若干功能、颜色变多或文件变少，都不自动代表画质提升。不要写总分或宣称优于另一个未使用的版本。对审美意见说明目标背景、原尺寸表现和代价；未看图不声称视觉验收。

结束后打包 RUN 目录，并提供原始可见会话。不要改写 runner 已冻结的文件；后续说明另存到 RUN 之外。
